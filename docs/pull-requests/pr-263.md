# [PR 263](https://github.com/vig-os/scitadel/pull/263) fix(db): make run_migrations transactional and locked against concurrent starts

## Problem

`run_migrations` ran each migration through a bare `conn.execute_batch`, so every migration autocommitted on its own and no lock was held across the read of `schema_version`.

Two reachable failures, both in the documented TUI + MCP two-pane workflow where two processes open one database file:

1. **Not atomic.** A migration failing partway left earlier statements committed. The next start re-ran it and hit `duplicate column name`, wedging the database permanently.
2. **Not locked.** Two migrators starting together both read an empty `schema_version`, both concluded nothing had been applied, and both ran the same `ALTER TABLE`. The loser failed.

## Fix

The whole run happens in one `BEGIN IMMEDIATE` transaction, taking the write lock *before* `schema_version` is read. The loser of a race blocks on the lock, then observes the winner's committed versions and skips them.

A contended caller is also given a `busy_timeout` first — `run_migrations` is reachable through a bare `Connection` that never went through `Database::open`'s init closure.

Version rows are now recorded in Rust as well as by the `.sql` files, so version-gating holds by construction even if a future migration forgets to self-record. `migrations` became a parameter (production always passes `MIGRATIONS`) so atomicity can be tested against a synthetic failing migration.
