# [PR 264](https://github.com/vig-os/scitadel/pull/264) fix(credentials): keep secrets off argv and out of Debug output

## Problem

`security_store` shelled out to `security add-generic-password -w <value>`, putting the plaintext in the process table for the lifetime of the command — readable by any local user with `ps`.

## The suggested fix would have been worse than the bug

The issue proposes passing a bare `-w` so `security` prompts and the value arrives on stdin. It does not prompt. Apple's SecurityTool source (`keychain_add.c`) parses with:

```c
getopt(argc, argv, "a:c:C:D:G:j:l:s:p:w:UAT:")
...
case 'p':
case 'w':
    passwordData = optarg;   // no prompt fallback
```

`w:` requires an argument, so a bare trailing `-w` stores an **empty** password, and `-w -U` consumes `-U` as the password. Only the framework API keeps the value out of argv.

## Fix

- `get`/`store`/`delete` now call `security-framework` directly (macOS-gated dependency) instead of the CLI. No subprocess, no argv.
- Calling the framework keeps **scitadel** as the item's trusted application, which preserves the prompt-free reads the CLI was chosen for.
- Values are carried in a `Secret` newtype: redacted `Debug`/`Display`, zeroized on drop, deliberately **not** `Serialize`. A secret cannot reach an HTTP body, config dump or TUI snapshot without a deliberate `expose()` at a greppable site.
- `Backend::MacosKeychain` is now `cfg(target_os = "macos")`. Compiling it out means `SCITADEL_CREDENTIAL_BACKEND=macos-keychain` on Linux degrades to auto-detection rather than selecting an unimplementable backend. The Keychain needs no reachability probe, so the `security`-on-PATH check is gone and `select_backend` lost an argument.

## Migration note for existing users

An item written by an older scitadel carries an ACL trusting `/usr/bin/security`, so the first read by scitadel itself may raise a **one-time** Keychain authorization prompt. Re-running `scitadel auth login <source>` rewrites the item with an ACL that trusts scitadel and clears it. Items are found either way — both paths use `kSecGenericPassword` with the same service and account.

| Test | Old behaviour | New |
|---|---|---|
| `secret_tool_store_keeps_the_secret_out_of_argv` | FAILED — `the secret reached the process argv, readable via ps` | pass |

The argv test installs a fake `secret-tool` that records both argv and stdin, so it runs on Linux CI and pins the property on the one store path that still shells out. The macOS round-trip exercises a real Keychain on the existing `macos-latest` runner.

**The macOS path was compile-verified locally** via `cargo check --target aarch64-apple-darwin --all-targets` (the macOS-only code and tests type-check), but could not be *run* here — that is what the macOS runner is for.

Full workspace suite green (23 test binaries). `cargo fmt --check` and `clippy -p scitadel-core --all-targets -D warnings` clean. `clippy --workspace` still fails on a pre-existing unknown-lint in `scitadel-mcp` under the locally-installed toolchain, present on `origin/dev`.
