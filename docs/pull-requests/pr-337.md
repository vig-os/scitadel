# [PR 337](https://github.com/vig-os/scitadel/pull/337) fix(adapters): cap the fetched body during the streaming read

## Problem

ADR-007 §1 specifies per-kind size caps (full text 100 MB, SI 250 MB,
figure/table 20 MB). `scitadel-adapters/src/download.rs` pulled the
whole body into memory via `response.bytes()` on every ladder leg, with
no cap. A route reaching a publisher serving a multi-gigabyte file
would stage the bytes, hash them, and file a `blobs` row — ADR-007
§1's cap was wired only on local files (#286), and the cap on the next
`scan` would never run because the bytes were already filed.

## Fix

- **`scitadel-http`** — new `PacedResponse::bytes_capped(cap)` that
  enforces the cap *during the streaming read*. A declared
  `Content-Length` over the cap refuses early (nothing is pulled from
  the socket); a lying `Content-Length` is caught by the running read,
  because the enforced limit is the byte count and never the header.
  Dropping the reqwest response aborts the stream, so no partial bytes
  are passed to `store_bytes` and nothing is staged.
- **`scitadel-adapters`** — all three ladder fetch points
  (`fetch_candidate`, `preprint_candidate`, `download_body` /
  `download_publisher_html`) now use `bytes_capped`. The cap is
  `FETCH_BODY_CAP_BYTES`, a verbatim re-export of
  `scitadel_db::sqlite::CAP_FULLTEXT_BYTES` (which is itself
  `cap_for_kind("fulltext_pdf")`), so the one rule `scan` enforces and
  the one the fetch path enforces are the same number under two names.
  The constant is configurable through `PaperDownloader::with_body_cap`
  — tests drive it on sub-KiB bodies; production stays on 100 MB.
- A `too_large` row lands in `acquisition_attempts` alongside `scan`'s
  own refusals, with the kind (`fulltext`), the route, and a detail
  line that distinguishes the pre-flight refusal from the stream
  refusal. Recorded best-effort so an audit-row failure never masks
  the walk's error.
- New `LegOutcome::TooLarge { cap, observed, from_content_length }`
  so the ladder's own recording is honest: this is *our* refusal to
  file what came back, not the publisher's refusal to serve it
  (`Refused` is the publisher's answer; `TooLarge` is ours).

## Tests

- `scitadel-http` adds six `bytes_capped` tests: body exactly at cap,
  body just under cap, chunked body over cap, honest Content-Length
  over cap, a declared length under the cap is not a license to relax
  it, and a **lying** Content-Length driven through a raw TCP listener
  (because `hyper` on the server side refuses to send a body that
  disagrees with its Content-Length — the shape that would bite us in
  production goes through a raw socket).
- `scitadel-adapters` adds five end-to-end tests pinning the
  acceptance criteria: a chunked body over the cap records `too_large`
  and writes no blob (nothing in `blobs/`, nothing in `blobs/.tmp/`,
  no artefact row); a declared length over the cap refuses before
  reading; a body exactly at the cap is filed; a body just under the
  cap is filed; and `the_fetch_cap_is_the_same_rule_scan_enforces`
  asserts `FETCH_BODY_CAP_BYTES == cap_for_kind("fulltext_pdf") ==
  100 MB` — so a later edit to one side cannot drift from the other.

## Acceptance

- [x] A fetched body above the cap is never written to the blob store,
      and records `too_large`.
- [x] A lying `Content-Length` cannot raise the enforced limit.
- [x] A chunked response with no `Content-Length` is bounded.
- [x] `scan` and the fetch path share one implementation of the rule.

## Note on scope

ADR-007 §3 reaches more than fulltext (SI 250 MB, figure/table 20 MB),
but the live ladder today fetches only fulltext routes (arXiv,
OpenAlex, Unpaywall, publisher, preprint). The SI / figure routes the
issue mentions (Europe PMC, PMC OA, DataCite, Figshare) are not yet
wired to a byte-fetch — their calls through `.text()` are API-shaped.
The cap is already keyed per kind via `cap_for_kind`, so when those
routes land they can pass the right cap to `bytes_capped` without any
further plumbing.

Closes #288

### How it is surfaced

- Migration 015 extends `acquisition_state.status` with `too_large`.
- `Ladder::status()` emits `too_large` when any attempted leg is a `LegOutcome::TooLarge`; a walk whose terminal legs are all server refusals keeps `unavailable`. Both stay out of `ACQUIRE_QUEUE_STATUSES`.
- `ALL_STATUSES` names `too_large` with its own `action_list` heading: "fetch manually and import, or raise the body cap and re-acquire by id". The entry's `reason` carries the URL host (via `LegOutcome::TooLarge.url` → `Ladder::clause`), the observed / declared size, and the cap — rendered once from `LegOutcome::TooLarge` so the audit row (`acquisition_attempts.detail`) and the action-list reason cannot drift.

### How the caps are unified in every configuration

- `scitadel_db::sqlite::cap_for_kind_with_override(kind, override)` is the single per-kind resolver.
- `PaperDownloader::with_body_cap_override` (fetch) and `ScanOptions::from_body_cap_override` (scan/attach) both carry the same `Option<u64>` from `config.acquire.body_cap_bytes` into it.
- The override replaces only the fulltext row of the per-kind table — raising it admits a larger fulltext on both paths without touching SI, figure or table caps. `cap_for_kind_with_override("fulltext_pdf", None) == cap_for_kind("fulltext_pdf") == FETCH_BODY_CAP_BYTES` is pinned by `the_fetch_cap_is_the_same_rule_scan_enforces`.
