# [PR 279](https://github.com/vig-os/scitadel/pull/279) fix(http): give doi.org its own pacing bucket, with a sourced interval

Closes #275. Unblocks S2's pre-fetch identity check.

## The defect was subtler than "no bucket"

The issue said `doi.org` had no pacing bucket. It had one — **named** `doi.org`, because that is its registrable domain. So any check on the bucket name reported it as handled, while it silently carried the unknown-host **policy**: 5 s minimum interval, 500 requests.

A 1,889-DOI corpus is **2 h 37 m** of pure resolution before a single PDF is fetched.

My first version of the routing test asserted the bucket name and **passed with the entry removed** — it was testing the thing that was already fine. It now compares policies, which is what was actually wrong:

```rust
assert_ne!(route.policy.min_interval_ms, unknown_policy.min_interval_ms,
          "{host} still carries the unknown-host policy");
```

## Where the numbers come from

I refused to invent a limit, so I went looking and then measured.

**doi.org's own resolution documentation publishes no rate limit** for the proxy. A probe of 30 sequential resolutions (~1.9 req/s) returned no 429 and **no rate-limit headers at all**. The service is deliberately unmetered on this path.

The only *published* number that names doi.org is DataCite's, for requests arriving via doi.org content negotiation:

> Requests that come via doi.org Content Negotiation have a rate limit of 1000 requests per 5 minutes per IP address.

That is ~3.3 req/s. The registered interval is **500 ms** — 2 req/s, under a ceiling that is *inferred* rather than observed.

| | value | source |
|---|---|---|
| `min_interval_ms` | 500 (2 req/s) | DataCite's cited 1000/5min, with headroom |
| `request_cap` | 1,000 / rolling 24 h | **our policy choice**, labelled as such |

The cap is deliberately conservative and labelled in the table, because a policy table with unattributed numbers is one nobody can audit. A real campaign resolving 1,000 distinct DOIs will raise it — and the right response is **caching**, not a bigger unsourced number: doi.org's proxies cache handle values with a **24 h TTL**, so re-resolving an unchanged DOI is both wasteful and unnecessary.

## Verification

Three tests, each confirmed to fail with the entry removed:

- `doi_org_is_routed_rather_than_inheriting_the_unknown_host_policy`
- `doi_org_pacing_is_far_below_the_unknown_host_default_and_under_the_cited_ceiling`
- `the_doi_org_cap_is_the_documented_policy_choice`

The second asserts both directions — materially faster than the default (the point of routing it), and still above 300 ms so it cannot drift up past the cited ceiling.

732 tests pass across 26 binaries. `fmt --check` clean. Clippy `-D warnings` clean on the pinned 1.98.1 toolchain.

## Not done

Resolution **caching** (issue item 4) is not implemented — it belongs with S2's identity check, which is what would call it. This PR removes the crawl that would have made S2 unusable.
