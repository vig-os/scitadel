# [PR 302](https://github.com/vig-os/scitadel/pull/302) ci(vhs): tui-papers runs five tapes on a ten-minute budget and dies at the ceiling

#274 says "the ffmpeg+ttyd install step is cancelled on a 10-minute timer, failing unrelated PRs". **That is not what happens**, and the distinction decides the fix.

Measured on the failing job, on `dev` and on branch:

```
X The job has exceeded the maximum execution time of 10m0s
✓ Install ffmpeg + ttyd          <- the step finishes
✓ Install vhs
✓ Build scitadel
✓ Run shard tapes
✓ Assert tapes produced distinct snapshots
✓ Upload tape artifacts
```

Every step succeeds. The job is then killed at its own ceiling, so the **`timeout-minutes` on the shard** is the whole problem. Nothing about `ttyd` or `ffmpeg` install is involved.

```yaml
timeout-minutes: ${{ matrix.shard.timeout-minutes || 10 }}
```

That is a job-level expression, and only `tui-reader` sets the matrix field — at 14m. **`tui-papers` declares five tapes, the same count as `tui-reader`, and falls back to 10m.**

The shard-budget comment already in this file does the arithmetic: ~3m of fixed build + install overhead, then 60-90s per TUI tape. Five tapes is **8-10.5m against a 10m ceiling**, so the shard passes only when the install is fast. That is why this reads as a flake, and why it fails on `dev` itself — not just on branches.

Give it the same 14m `tui-reader` already has for the same tape count. Shards run in parallel, so total wall-clock is unchanged, matching the comment already here.

This is what blocked PR #301 and every other PR: three of its checks (`Tape coverage`, `Tapes`, `Run tapes (tui-papers)`) were red for this reason on `dev` as well, with all 20 real checks green.

## Separate, and still open

`tests/vhs/papers-download-state.tape` declares two screenshots and only produces one (`02-quit.png` is a quit frame, so the app exits before the capture lands). That is an annotation, not this failure — the distinctness assertion passes — and it is the same tape gap already noted in the #254 work. It wants its own fix: either capture before quit, or drop the second declared frame and cover the success path it was meant to cover.
