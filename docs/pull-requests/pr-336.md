# [PR 336](https://github.com/vig-os/scitadel/pull/336) fix(mcp): confine bib read paths to the workspace, drop the agent-supplied output on bib_snapshot

## Problem

The same caller-controlled-path shape #249 removed from `download_paper` was still present on four other MCP tools:

| Tool | Field | Direction |
|---|---|---|
| `import_bibtex` | `path` | agent-supplied file **read** |
| `bib_diff` | `file_a`, `file_b` | agent-supplied file **reads** |
| `bib_verify` | `file` | agent-supplied file **read** |
| `bib_snapshot` | `output` | agent-supplied file **write** — same arbitrary-write class as #249 |

An agent — including a prompt-injected one — could exfiltrate arbitrary files via the three reads, or aim a scitadel-generated snapshot at `~/.config/autostart`, `.githooks/`, a shell rc, etc. via the write.

## Fix (per owner decision, 2026-11-09)

- **Reads** are confined to the workspace root. A caller-supplied path is canonicalised (symlinks followed) and must sit under the root, otherwise refused with a clear typed error. Relative paths resolve against the workspace, not the process CWD.
- **Export output** is no longer caller-supplied. `bib_snapshot` generates the filename from `question_id` + format and writes under `.scitadel/bib/` — the #249 pattern lifted.
- **CLI keeps its current behaviour.** A human on the CLI can still pass any path; only the MCP surface is scoped.
- **One shared helper** (`scitadel_mcp::paths`) owns the rule so future MCP tools cannot forget it — DRY, as the owner asked.

The helper:

- `workspace_root(&Config)` — derived from `db_path`'s grandparent, canonicalised (so macOS `/tmp` → `/private/tmp` stays stable through `starts_with`).
- `confine_to_workspace(root, user_path)` — resolve, canonicalise, `starts_with` check. Returns a typed `PathScopeError { WorkspaceInaccessible | Escapes | NotAccessible }`.
- `confine_read_path(user_path)` — convenience that pulls root from the active config, called by every MCP read tool.
- `mcp_export_dir(&Config)` — the paired write-side helper for `bib_snapshot`.
- `sanitize_filename_component` — strips `.` as well as path separators so a `question_id` of `..` can never become a path-special component.

The schema loses `BibSnapshotRequest.output` entirely, so the field is gone from the JSON schema an LLM reads — same shape as #249's `DownloadPaperRequest`. Older callers that still send `output` have it dropped by serde (no `deny_unknown_fields` is used in this crate).

## Tests

Every acceptance-list case has an explicit test:

**Helper unit tests** (`paths::tests`, 7):

- `..` traversal — refused
- absolute path outside root — refused
- symlink pointing outside root — refused
- symlink *inside* root pointing outside — refused (the case the issue calls out by name)
- happy path inside root — accepted, returns the canonical path
- missing file — distinct `NotAccessible` error (not `Escapes`)
- `sanitize_filename_component` — path separators and `..` cannot survive; all-stripped input falls back to a fixed label

**End-to-end tool tests** (`server::tests::mcp_path_scoping_tests`, 7):

- `import_bibtex` inside-root happy path
- `import_bibtex` refuses `..` traversal
- `import_bibtex` refuses absolute outside-root
- `import_bibtex` refuses symlink inside root pointing outside (`#[cfg(unix)]`)
- `import_bibtex` refuses symlink outside root (`#[cfg(unix)]`)
- `bib_diff` refuses traversal on either side
- `bib_verify` refuses absolute outside-root

**Schema / structural tests** (`server::tests`, 3):

- `bib_snapshot_schema_offers_no_output_path` — the JSON schema an LLM reads carries no `output` / `outputPath`; properties are exactly `{format, no_lock, question_id, reader}`
- `bib_snapshot_request_ignores_a_supplied_output_path` — an injection-style payload with an `output` key parses successfully but the destination is nowhere on the struct
- `read_path_schemas_name_exactly_their_path_fields` — pins the field set of `ImportBibtexRequest` / `BibVerifyRequest` / `BibDiffRequest` so a future field cannot bypass the confinement helper
- `bib_snapshot_lands_under_scitadel_bib_regardless_of_request_shape` — end-to-end: even when an extra `output` key is smuggled in, the snapshot still lands under `.scitadel/bib/`

## Acceptance

- [x] No MCP tool accepts a caller-supplied directory, and no caller-supplied path escapes the workspace boundary.
- [x] Traversal, absolute-outside-root and symlink-out cases are all refused, each with a test (both at the helper and at the tool boundary).

## Verification

`scitadel-mcp` suite: 95 tests green, including the 7 new helper tests, 7 new end-to-end scoping tests, and 4 new schema/structural tests. Full workspace clippy under the pinned toolchain is clean.

### Round 4 — final design

Three adversarial rounds all traced back to one shared root cause: **two independent notions of "the project" lived in the tree**. `scitadel_core::config` picked a workspace from `git rev-parse --show-toplevel` with a fallback to cwd, and `Database::open` auto-`create_dir_all`'d the DB parent — so the first DB call from the MCP server seeded a fresh `.scitadel/` marker in the launching directory (`~/Projects`, `/tmp`, …). The MCP path rule in `scitadel_mcp::paths` then walked up from cwd and happily accepted that freshly-created broad dir as its confinement root.

#### The shared resolver

`scitadel_core::project::project_root` is now the single source of truth. Both config/DB placement and MCP confinement route through it. Resolution rule:

1. `SCITADEL_WORKSPACE` if set — the override must itself contain a `.scitadel/` marker.
2. Walk up from cwd for the same marker.

No other fallback. `GIT_WORK_TREE` / `GIT_DIR` are never consulted. The MCP server **never creates** the marker; the CLI's `scitadel init` still does. `load_config` keeps its cwd fall-back so `scitadel init` can seed a fresh project *before* the marker exists, but no longer shells out to git. The marker itself is validated: it must be a real directory, or a symlink whose canonical target is still inside the project; a plain file or an outside-pointing symlink is refused. A root at `/`, `$HOME`, or any ancestor of `$HOME` is refused — both `$HOME` (raw + canonical) AND `getpwuid` (raw + canonical) are compared, so a spoofed `HOME` cannot disarm the check.

#### Server startup behaviour

**The server starts even without a marker** — DB and path tools then return a single uniform error naming the fix (`scitadel init`, or set `SCITADEL_WORKSPACE`). Refusing to start would break the documented user-scope install (`claude mcp add --scope user -- scitadel mcp`), which launches the server in every Claude Code session including ones outside a scitadel project. Credential-only tools stay reachable.

#### Uniform error

Any path that resolves outside the project — `..` traversal, absolute-outside, symlink leaf outside, symlink in the middle whose target points outside, **or** dangling symlink at any depth whose named target would be outside — yields the same `OutsideWorkspace` error, byte-identical apart from echoing the caller's input. No existence oracle survives through any symlink at any depth.

#### Safe-write

- Tempfile `O_CREAT | O_EXCL | O_NOFOLLOW`, atomic `rename`.
- Existing-file mode preserved **masked with `0o777`** — setuid, setgid and sticky bits never cross a write.
- Parent canonicalised + `starts_with(root)`. A parent symlink inside the root pointing to another inside-root dir is allowed; one pointing outside is refused.

#### Safe-read

- Linux: `openat2(RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS)` against the workspace-root FD so the kernel refuses to cross the project boundary **and** refuses to follow any symlink below root. Falls through to the generic path on `ENOSYS` (kernel < 5.6).
- Fallback: `O_NONBLOCK | O_NOFOLLOW` on open, `fstat` the handle, refuse anything that is not a regular file — a FIFO / device / socket in the workspace can never hang `read_to_string`.
- Errors render workspace-relative paths; the absolute root never leaks.

#### Residual risk

An intermediate-directory swap race between parent canonicalisation and the tempfile open for **writes** is unmitigated. `openat2` closes it for reads on Linux; the analogous `renameat2` walk for writes is noted in the module rustdoc as out of scope for this PR.

### Round-6 close-out: threat model, command matrix, and pass-5 mapping

Head: `7273716`.

#### Threat model (now in `scitadel_mcp::paths` rustdoc and the README's MCP section)

**In scope.** Every MCP request field, the user's config and environment, DB-supplied paths an earlier MCP call wrote. An agent — including a prompt-injected one — whose only lever is what it can send over the MCP transport is the attacker this module is written for.

**Out of scope.** Local processes or users with write access to the project tree: `renameat2(RENAME_EXCHANGE)` swaps of `.scitadel/` or any intermediate dir mid-call, hardlinking another project's DB into `.scitadel/`, bind mounts, and the TOCTOU races they enable. An attacker at that level can already read what MCP reads and write anywhere the user writes, so MCP confinement cannot protect against them. Root is likewise out of scope.

**Residual races.** `openat2(RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS)` on Linux ≥ 5.6 closes every path-canonicalisation race for an MCP-only attacker. The non-`openat2` fallback (older Linux, macOS, other Unix) re-opens the canonical path after the walk; an attacker with directory-swap write access to the project tree could still aim the read elsewhere. Documented in one place in the rustdoc, not fixed.

#### Command matrix — who creates `.scitadel/` in an empty dir?

| Command | Creates `.scitadel/`? | Why |
|---|---|---|
| `init` | **Yes** | The one documented creator. |
| `search`, `assess`, `download`, `acquire` (real), `snowball`, `scan`, `attach`, `bib import`, `bib watch`, `question create`, `question add-terms`, `override-identity`, `resolve-doi` (save), `import-flat` | **Yes** | Write-side auto-initialisation; a first real acquisition in a fresh tree still Just Works. |

| `bib verify` | Only if it opens the DB today | Pre-existing shape; untouched. |
| `auth *`, `themes`, `--help`, `mcp` | No | No project needed, or (`mcp`) the server itself is sticky on marker-less. |
